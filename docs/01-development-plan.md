# 01. План разработки сервиса

Цель: персональный планировщик подготовки для 2 пользователей (ты и девушка), без платных зависимостей. Источник контента — этот репозиторий. Никакого «красивого UI»: функциональность важнее.

## 1. Решение по формату (рекомендация)

**Основной продукт — веб-приложение, бот — только уведомления.**

Почему: карточки, таймер, редактор эссе со счётчиком слов, запись голоса и журнал ошибок неудобны в Telegram. Бот хорош для «сегодня у тебя 5 заданий, вот ссылка».

| Слой | Выбор | Причина |
|---|---|---|
| Фронтенд/бэк | Next.js (App Router, TypeScript) | один код, SSR не нужен, но удобно |
| Хостинг | Vercel (бесплатный тариф) | деплой из GitHub |
| БД + авторизация | Supabase (Postgres, Auth, RLS) | профили 2 людей, прогресс, изоляция данных |
| Контент | YAML/MD в репозитории → сид в БД | git = история и бэкап |
| SRS | алгоритм FSRS (open-source, есть реализация для TypeScript — проверь актуальный пакет) | лучше классического SM-2 по эффективности [E] |
| Проверка Writing/Speaking | «Copy prompt» → вставка в любой чат-ИИ → вставка JSON-ответа обратно | $0, без API-ключей |
| Бот | Telegram Bot API + Vercel Cron | утренний пуш |
| Fallback | `skill/SKILL.md` | работает без сервиса |

Бесплатные тарифы и лимиты Vercel/Supabase проверь перед запуском — они меняются.

## 2. Этапы и приёмка

**Этап 0 — Контент-основа (3–5 дней).** Репозиторий, `resources.yaml`, `check_links.py`, ручная проверка всех `to_verify` ссылок. *Приёмка:* ≥90% ссылок с `status: verified`, для каждого навыка ≥3 ресурса.

**Этап 1 — Skill-режим (1–2 дня).** Отладить `skill/SKILL.md` на 2–3 разных ИИ. *Приёмка:* на тестовых ответах ИИ строит профиль и план без выдуманных ссылок.

**Этап 2 — MVP сайта (1–2 недели вечерами).**
1. Auth (email magic link), 2 пользователя, RLS «каждый видит только своё».
2. Мастер интейка (анкета → профиль).
3. Страница «Сегодня»: список заданий, отметка выполнения, время.
4. Журнал ошибок (теги из `skill/SKILL.md`).
*Приёмка:* вы оба можете зайти, пройти анкету и получить задания на день.

**Этап 3 — SRS и словари (1 неделя).**
- Скрипт импорта: NGSL/Oxford/AWL/NAWL/AVL → карточки (слово, часть речи, пример, коллокации, уровень).
- Карточки хранят **chunk + пример**, а не голое слово.
- Дневной лимит новых — настраиваемый (стартово 8–12; цель — удержание ≥85–90%, а не количество). 30 новых слов в день, как в твоём примере, обычно приводит к лавине повторений [E].
- Экспорт в Anki CSV (запасной вариант).
*Приёмка:* 200 карточек, ежедневные повторения считаются корректно.

**Этап 4 — Writing/Speaking-петля (1 неделя).**
- Таймер + счётчик слов; сохранение эссе.
- Генератор промпта проверки (критерии + public band descriptors + якорные примеры с известными оценками + ответ в JSON).
- Импорт JSON-оценки → график динамики по критериям.
- Speaking: запись в браузере (MediaRecorder), транскрипт — опционально через Web Speech API; пара-режим «экзаменатор/кандидат» для вас двоих.
*Приёмка:* полный цикл «эссе → промпт → оценка → ошибки в журнал → задания на исправление».

**Этап 5 — Планировщик (1–2 недели).** Реализовать алгоритм из раздела 4. Юнит-тесты на распределение часов и на перенос пропущенных дней.

**Этап 6 — Telegram-бот (2–3 дня).** Утренний пуш + «сегодня» + кнопка «сделал». Данные только из БД.

**Этап 7 — Каждые 4 недели:** мок-тест, пересчёт профиля, автокорректировка плана. Это постоянный режим, не разовая задача.

## 3. Схема данных (Postgres, упрощённо)

```
profiles(id, user_id, display_name, module [academic|general], target_overall, target_min_per_skill,
         test_date, hours_per_week, created_at)
skill_state(profile_id, skill [L|R|W|S], current_band, target_band, confidence, updated_at)
weakness_tags(profile_id, tag, severity 0-1, last_seen)
plan_weeks(profile_id, week_no, phase, hours_budget, allocation jsonb)
tasks(id, profile_id, date, skill, type, resource_id, minutes, status, result jsonb)
resources(id, ...поля из resources.yaml)
cards(id, lemma, pos, example, collocations jsonb, list_source, level)
card_state(profile_id, card_id, due, stability, difficulty, last_review, state)  -- FSRS
errors(profile_id, date, skill, code, snippet, fix, reviewed_at)
submissions(profile_id, kind [W1|W2|S1|S2|S3], text/audio_ref, self_band, llm_band jsonb, created_at)
mocks(profile_id, date, L, R, W, S, overall, source)
```

Правила: RLS по `profile_id → auth.uid()`. Аудио не хранить на сервере (локально в браузере), только транскрипт и оценки.

## 4. Алгоритм планировщика

Вход: профиль, `skill_state`, `weakness_tags`, недели до теста, бюджет часов.

1. `gap_s = max(0, target_s − current_s)` для каждого навыка.
2. Вес навыка: `w_s = 0.10 + 0.60 · gap_s / Σgap` (минимум 10% на каждый навык, чтобы не терять форму), нормировать до суммы 1. Если `Σgap = 0`, равномерно.
3. Корректировка: `+0.05` навыку, где есть ≥2 тегов с `severity > 0.6`; `+0.05` Writing и Speaking, потому что у них самый долгий цикл обратной связи.
4. Часы недели = `hours_per_week · w_s`. Разбить на сессии по 25–45 минут.
5. Для сессии выбрать тип задания по фазе (см. 02) и **слабому тегу**: если частый код ошибки `L-SPELL` → диктант/spelling-drill; `R-TFNG` → тренировка именно T/F/NG на коротких отрывках.
6. Ресурс выбирается из `resources.yaml` по фильтрам: навык, уровень, `ru_risk=false`, `status=verified`, ещё не использован (или давно).
7. Пропущенные дни: не «догонять» лавиной; перенос максимум 30% объёма, остальное — отбросить и записать в статистику.
8. Каждые 4 недели: мок → обновить `skill_state` → пересчитать `w_s` и фазу.
9. Каждый день: ≥1 сессия SRS (≤15–20 мин) + 2–3 навыковых блока, итого ~1.5–2 ч в будни.

## 5. Генерация проверки Writing/Speaking (калибровка)

Зависимость от LLM-оценок — главный риск качества. Меры:
- В промпт включать **public band descriptors** и 2–3 якорных ответа с известными баллами (например, с официальных/проверенных источников) как эталон.
- Просить **диапазон** (например, «6.5–7.0») и цитаты-обоснования по каждому критерию, а не одно число.
- Раз в месяц сравнивать оценки двух разных ИИ и свою; расхождение >0.5 → считать оценку неуверенной.
- [E] LLM-оценки могут быть завышены или нестабильны, поэтому используй их как инструмент поиска ошибок, а не как «официальный» балл. Для финальной уверенности — единичные платные проверки у сертифицированного экзаменатора перед тестом (опционально, 1–2 раза).

## 6. Риски

| Риск | Митигация |
|---|---|
| Мёртвые/блокируемые ссылки | `check_links.py` раз в месяц, `status` в YAML |
| Юридический риск из-за BC (РФ) | `ru_risk` фильтр, не публиковать на публичной странице, приватный репозиторий |
| Авторские права | в репозитории только ссылки и оригинальные тексты; не класть чужие тесты/книги |
| Выгорание | недельный «лёгкий день», пропуск ≠ провал, метрика — стабильность |
| Лимиты бесплатных тарифов | экспорт данных, фолбэк на skill-режим |
| Слепая вера в ИИ-оценки | раздел 5 |

## 7. Что построить первым

Этапы 0 → 1 дают рабочую систему уже сейчас. Сайт (этапы 2–5) — когда убедитесь, что методика держится 3–4 недели: так вы не будете автоматизировать то, что не работает.
